## 2. Run the spike

- [x] 2.1 Dispatched [run 34679354748](https://github.com/bhoopathyvm-cloud/smaraAccount/actions/runs/34679354748) on `main`. Concurrency was not a bottleneck at all — 37 of 43 jobs were already `in_progress` within 60 seconds of dispatch. But every one of the 43 jobs' "Run the full acceptance suite" step was cancelled between 8.3 and 12.4 minutes after it started (average 11.4 min), regardless of each job's own absolute start time (spread across ~15 minutes of wall clock) — this is a per-job ceiling intrinsic to the `ubuntu-slim` runner class reclaiming/preempting the runner, not the `timeout-minutes: 360` setting (which only bounds the job from GitHub Actions' side and cannot override the runner's own infrastructure limit). This also explains why the original, unrelated `localized-smoke.yml` already used `timeout-minutes: 15` on this same runner label.
- [x] 2.2 Before being cut off, `pa` (Punjabi) passed 21 of 37 tests (~5 of 13 groups: currency_transfers, group_archive, home_and_lock, identity_restore, investment_holdings) in the ~10.5 minutes it got — no failures, no locale-specific bugs surfaced in what ran. Extrapolating that pace, the full suite likely finishes in roughly 20 minutes on Linux, which would easily fit even a modest timeout — the blocker is entirely the runner class, not the suite's real Linux runtime. `ubuntu-slim` is unsuitable for this spike; `ubuntu-latest` (already proven to support multi-hour jobs via `linux-desktop.yml` and known not to have this reclaim behavior) is needed instead.

- [x] 2.3 Switched to `ubuntu-latest` and re-dispatched: [run 34681112956](https://github.com/bhoopathyvm-cloud/smaraAccount/actions/runs/34681112956). **This time the run fully completed — no cancellations.** All 43 jobs finished in 10.4-12.2 minutes each (avg 11.0 min, including build-dependency install, Flutter setup, and Xvfb/D-Bus/keyring startup, not just the test step itself) — roughly **40-50x faster than the measured 8-10h macOS runtime**, and comfortably within the 6h cap with enormous headroom. 37/43 locales passed all 37 tests; 6 failed (`as`, `bn`, `ks`, `mni`, `mr`, `ne`).
- [x] 2.4 Re-ran just the 6 failing locales on a throwaway branch (matrix narrowed to those 6, never merged) to rule out CI-concurrency flakiness: [run 34682599778](https://github.com/bhoopathyvm-cloud/smaraAccount/actions/runs/34682599778). **All 6 failed again, at the exact same tests with the exact same pass/fail counts as the first run** — this rules out flakiness; these are real, deterministic, locale-specific bugs. Two distinct root causes, not one: (1) `as`, `bn`, `mr`, `ne` all fail identically at `investment_holdings employer-match buy with lock-until blocks selling the locked unit` with `WidgetController.tap()`'s internal `_maybeViewOf` throwing `Bad state: No element` (`recordNonCashBuyThroughGui`, `acceptance_test.dart:1632`) — a Flutter-test-framework/view-resolution issue, not a text/translation problem. (2) `ks` and `mni` fail in `ledger_backup`'s restore-dialog flow with `setState() called after dispose()` in `SettingsView._showRestoreBackupDialog` plus a finder assertion failure; `mni` additionally fails 2 `currency_transfers` tests. Both are genuine bugs worth their own investigation, but fixing them is out of this spike's scope per design.md's Non-Goals (37/43 locales already produce a clean, real result — this doesn't block getting a signal).

- [x] 2.5 Fixed the `as`/`bn`/`mr`/`ne` bug: `localizedDay()` added to `acceptance_harness.dart`, reproducing `MaterialLocalizations.formatDecimal`'s exact `intl.NumberFormat.decimalPattern` call so the test searches for the day number as it's actually rendered (native-script digits for these locales), not assumed ASCII. Verified via a new unit test (`test/acceptance_localized_day_test.dart`), the full `flutter test` suite (904/904 green), and confirmed on the real Linux CI runner: [run 34684351188](https://github.com/bhoopathyvm-cloud/smaraAccount/actions/runs/34684351188) — all 4 locales pass 37/37 clean, not just locally.
- [x] 2.6 `ks` and `mni` turned out to have **two different bugs**, not one shared cause, despite the identical-looking initial symptom:
  - **`mni` — fixed and confirmed.** A real translation bug: `app_mni.arb`'s `editGroup` was byte-identical to `createGroup`, so `find.byTooltip(l10n.createGroup)` ambiguously matched 6 widgets (every group's edit button plus the create action). Fixed by reusing `renameAccount`'s already-attested "modify" verb instead of inventing new vocabulary. Confirmed on [run 34685855699](https://github.com/bhoopathyvm-cloud/smaraAccount/actions/runs/34685855699): `mni` now passes 37/37 clean.
  - **`ks` — still broken, and the ledger_backup pump-cycle fix (task 2.5's sibling change) made it worse, not better.** The same run shows the "Euro Group still visible" assertion no longer fails for `ks` (the pump-cycle fix worked for that specific symptom), but a *different*, previously-masked issue now surfaces as the test's primary failure: `setState() called after dispose()` in `SettingsView._showRestoreBackupDialog`'s failure branch (`settings_view.dart:545`), meaning `viewModel.restoreBackup()` resolved with `ok == false` *after* the dialog was already gone. Read `_showRestoreBackupDialog`'s "Replace" button handler (`settings_view.dart:498-549`): `onPressed` is gated by `isBusy ? null : ...`, but that gate only takes effect after a rebuild — `tapReliably`'s own retry-on-no-visible-progress loop could plausibly tap the button a second time before that rebuild lands, launching a second concurrent `restoreBackup()` call. The first succeeds and pops the dialog; the second later resolves (likely hitting the now-closed database) with `ok=false` and calls `setDialogState` on the already-disposed dialog — matching the exact symptom. **Not confirmed** — a hypothesis from code reading, not a live-debugged root cause. Worse: this failure now cascades and corrupts 10 unrelated subsequent tests in the same continuous run (`ofx_import`, `onboarding`, `organization` x8) rather than staying contained to `ledger_backup`, since a crash mid-test evidently isn't fully absorbed by `resetToFreshDevice`'s per-test cleanup. Left unfixed — this now looks like a real, pre-existing double-invocation race in production restore-dialog code, not a test-only issue, and deserves careful, dedicated investigation (ideally with live debugging) rather than another guessed change.

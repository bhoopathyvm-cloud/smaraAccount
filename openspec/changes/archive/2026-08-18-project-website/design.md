## Context

The repository currently has three audiences' worth of documentation, all
only reachable by already being in the repo: `README.md` (short pitch +
tamper-evident design + contributing pointer), `docs/user-guide.md`
(end-user walkthrough), and `Specs/architecture/smara-architecture.md` /
`smara-tech-guidelines.md` (internal engineering discipline). None of this
is a public destination someone could be sent a link to.

Two realistic ways to publish Markdown as a GitHub Pages site were
considered: GitHub Pages' native Jekyll build (zero custom tooling, but
only serves from the repo root or a `/docs` folder — colliding with the
existing `docs/user-guide.md`), and a custom-built static site generator
deployed via GitHub Actions (`actions/upload-pages-artifact` +
`actions/deploy-pages`), which can serve any directory's *build output*
regardless of what the source directory is named. The author chose the
second path with [MkDocs](https://www.mkdocs.org/) and the
[Material for MkDocs](https://squidfunk.github.io/mkdocs-material/) theme
specifically to keep the source directory named `pages/` and get a more
polished result (search, sidebar nav, dark mode) than GitHub's built-in
Jekyll themes, at the cost of one small, isolated Python build dependency
and a short GitHub Actions workflow.

## Goals / Non-Goals

**Goals:**
- A small, honest project site: what problem this solves, how it was
  actually built (the OpenSpec/AI-authored angle, since that's the
  project's own distinguishing story per `README.md`'s "About this
  project"), and technical documentation a visitor can trust reflects the
  real repo.
- Every page authored as plain Markdown — no hand-written HTML/CSS, no
  JavaScript framework to learn or maintain.
- Deployable and updatable with a minimal, fully-owned toolchain: one
  pinned Python dependency and a short GitHub Actions workflow, not a
  bespoke build system.
- Reachable at the author's own domain.

**Non-Goals:**
- A JavaScript framework, component library, or hand-rolled CSS — Material
  for MkDocs already provides navigation, search, and theming out of the
  box; adding more on top would be exactly the kind of speculative tooling
  `smara-tech-guidelines.md`'s Golden Rules already argue against for the
  app itself, and the same discipline applies here.
- A blog, CMS, or comments system. "Give updates" (the author's stated
  goal) is served by adding/editing a Markdown page and pushing — no
  dynamic backend is needed or wanted, consistent with the project's own
  no-server stance.
- Automating the DNS change itself — no tool available to this change can
  reach the author's domain registrar. This change produces the exact
  DNS records needed and documents them as a manual task.

## Decisions

- **MkDocs with `docs_dir: pages` in `mkdocs.yml` at the repo root.**
  MkDocs' own default source-folder name is `docs/` — overriding it via
  `docs_dir` is a one-line config, not a workaround, and is what keeps the
  source directory named `pages/` (the author's original preference)
  without colliding with the existing `docs/user-guide.md`. `mkdocs.yml`
  itself lives at the repo root, per MkDocs' own convention of looking for
  it in the working directory it's invoked from.

- **Material for MkDocs, default configuration, no custom CSS.** Gets
  navigation, search, and a light/dark toggle for free; a custom theme or
  hand-written CSS on top would reintroduce the complexity switching away
  from hand-written HTML was meant to avoid.

- **Four pages, not one long page**: `index.md` (problem + solution),
  `how-it-was-built.md` (the OpenSpec/AI-authored story), `architecture.md`
  (technical documentation), `whats-built.md` (capability listing from
  `openspec/specs/`). Kept as separate files rather than one scrolling
  page so each can be linked to individually and updated independently —
  matches the author's stated goal of using this to "give updates." Nav
  order and titles are declared explicitly in `mkdocs.yml`'s `nav:` list
  rather than inferred from file names, so the site's structure is
  visible in one place.

- **Architecture page links back to the repo rather than mirroring
  `Specs/architecture/` verbatim.** Copying the full internal docs onto
  the public site creates two copies that drift the moment either is
  edited — the same reasoning `CONTRIBUTING.md` already used for linking
  to those docs instead of restating them (`project-documentation`
  change). The public page summarizes the stack/layering/security stance
  in visitor-friendly terms and links to the actual files in the repo for
  anyone who wants the full detail.

- **"What's built" page is generated by hand from `openspec/specs/`
  at write time, not by a script that reads the directory at build
  time.** A build-time generator is exactly the kind of tooling this
  design's Non-Goals rule out for a project this size; re-running the
  update-this-page task each time a change is archived (already a
  manual step in the OpenSpec workflow) is a small, honest cost instead.

- **GitHub Actions deploy, not the classic Pages-from-branch setting.**
  The workflow installs Python, installs the pinned `mkdocs-material` from
  `requirements.txt`, runs `mkdocs build` (producing `site/`, MkDocs'
  default output directory — left un-committed, build-only), then uploads
  `site/` via `actions/upload-pages-artifact` and deploys via
  `actions/deploy-pages`. This is the currently-recommended GitHub Pages
  setup and the only way to publish a directory GitHub's native build
  doesn't know about.
  - Workflow triggers on push to `main` **scoped to `pages/**`,
    `mkdocs.yml`, `requirements.txt`, and the workflow file itself**, so
    an app-only commit doesn't redeploy the site (and, conversely, an
    app-only CI run in `flutter-ci.yml` doesn't need to know the site
    exists).
  - `requirements.txt` pins `mkdocs-material` to a specific version,
    resolved at implementation time — matching the same "commit the
    lockfile, everyone resolves the same graph" discipline
    `smara-tech-guidelines.md` already states for Flutter dependencies,
    applied to this second, isolated toolchain.

- **`CNAME` file contains `bhoopathy.com`** (the author's explicit
  choice — root domain, not a subdomain). This requires A/ALIAS records
  at the registrar rather than a single CNAME record, since apex domains
  generally cannot use a CNAME per DNS spec. Documented as a manual task
  with the exact records needed (see Migration Plan).

## Risks / Trade-offs

- [Choosing the root domain means `bhoopathy.com` becomes this project's
  landing page, not a personal one — the author may want the root domain
  for something else later.] → Mitigation: this was an explicit, informed
  choice by the author (offered a subdomain alternative first); changing
  it later is just editing the `CNAME` file and the DNS records, not a
  structural change to this site.
- [Hand-editing `whats-built.html` after each archived change is easy to
  forget.] → Mitigation: call it out as a step in this change's own
  tasks.md, and note it in `CONTRIBUTING.md`'s archive step as a reminder
  for future changes — kept as a documentation note, not new tooling.
- [GitHub Pages' IP addresses for A records are subject to change over
  time.] → Mitigation: tasks.md points the author to GitHub's own current
  documentation to confirm the exact addresses at setup time, rather than
  hard-coding them as unquestionable.

## Migration Plan

- Additive only: new `pages/` directory, `mkdocs.yml`, `requirements.txt`,
  and one new workflow file. No existing file changes, no risk to the app
  itself, no Flutter/Dart dependency graph changes.
- Manual, one-time setup (documented in tasks.md, not automatable from
  here): enable GitHub Pages in the repo's Settings → Pages, source
  "GitHub Actions"; at the domain registrar, add A records for
  `bhoopathy.com` pointing at GitHub Pages' published IP addresses (and
  optionally AAAA records for IPv6), per GitHub's current documentation.
- Rollback: delete `pages/`, `mkdocs.yml`, `requirements.txt`, and the
  workflow file, and remove the A records/disable Pages in Settings — no
  impact on the app.

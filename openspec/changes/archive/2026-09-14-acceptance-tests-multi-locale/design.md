## Context

The acceptance harness (`integration_test/acceptance/support/acceptance_harness.dart`) and the merged suite (`integration_test/acceptance/acceptance_test.dart`) currently hardcode `final l10n = AppLocalizationsEn();` at 6 call sites and never touch the app's language-selection screen beyond confirming "Same as device" (which resolves to English in the test environment). Every `find.text(l10n.xxx)` lookup, and every literal string the suite types into the app (category names, payee names, descriptions, search terms — roughly 35 `enterTextReliably`/`enterText` call sites), is therefore English by construction, not by an explicit choice the test makes per run.

The app itself already has everything a per-locale run needs: 43 ARB-backed locales, a mandatory first-launch language screen (`onboarding-language-selection`), a currency default that already varies by locale and needs no test change (the harness already just accepts whatever's pre-filled), and a recovery-phrase flow that already reads words dynamically off-screen rather than assuming English ones. What's missing is purely on the test side.

## Goals / Non-Goals

**Goals:**
- Reuse the entire existing ~4300-line suite unmodified in *structure* — no duplicated test bodies — across a curated set of locales, selected at compile time.
- Select the locale through the app's own real first-launch language screen; no test-only backdoor or platform-level locale override.
- Leave the default (no locale specified) invocation behaviorally identical to today's English-only run.
- Translate the fixture strings the suite types into the app for a curated locale set, not all 43 locales.
- Keep the new multi-locale entry point fully opt-in and outside CI, consistent with the acceptance suite's existing manual-only contract.

**Non-Goals:**
- Fixture translations for all 43 locales — only the curated set (9 initially; extensible).
- A smaller, localization-focused smoke suite — explicitly rejected in favor of running the existing full suite per locale, accepting the runtime cost as a manual/periodic tool rather than a CI gate.
- Grading translation quality/idiom — this exercises that the GUI functions correctly and round-trips text in each script/direction, not that the wording is natively fluent.
- Any change to app behavior under `lib/` — this is test-infrastructure only.

## Decisions

1. **Compile-time locale selection via `--dart-define`.** `acceptance_test.dart` reads `const _targetLocaleTag = String.fromEnvironment('ACCEPTANCE_LOCALE', defaultValue: 'en')` once. Alternatives considered: a runtime `Platform.environment` read — rejected, integration-test binaries on iOS/Android don't reliably forward host environment variables into the running app process; `flutter test --name` filtering — rejected, that only selects which tests run, it can't parameterize a value into them.

1a. **`materialL10n(tester)` bug found by the full English regression run itself** (not a locale-specific bug - present in every locale, including the original English path, until fixed): the first implementation resolved `MaterialLocalizations.of(tester.element(find.byType(MaterialApp).first))`, but `Localizations` is a *descendant* of `MaterialApp`, not an ancestor - looking up from the `MaterialApp` element's own context can't see it, throwing "No MaterialLocalizations found" the first time any group actually exercised the "Show menu"/"Back"/date-picker helpers (the `onboarding`-group smoke tests used earlier didn't touch that code path, so this stayed hidden until the full-suite run reached `group_archive`). Fixed by resolving from `find.byType(Scaffold).first`'s element instead - any rendered screen's `Scaffold` sits below `MaterialApp`'s internal `Localizations` wrapper.

2. **A locale-indexed `AppLocalizations` dispatcher** (`l10nFor(String tag)`, new file `integration_test/acceptance/support/localizations_for_tag.dart`) replaces the current hardcoded `AppLocalizationsEn()` at all 6 call sites. It's an exhaustive switch over `kSupportedLocaleTags` (all 43) returning the matching generated `AppLocalizationsXx()` — mechanical and cheap to keep exhaustive even though only the curated subset is exercised today, so adding a locale to the curated set later needs no dispatcher work. Alternative considered: fetch `AppLocalizations.of(tester.element(finder))` dynamically at each lookup — rejected as a much larger diff (every `l10n.xxx` reference would need a `BuildContext` in scope) for no benefit, since the target locale is already known statically for the whole run.

3. **Language-screen selection by endonym text.** For any tag other than `'en'`, the onboarding helper taps `find.text(endonymForLocaleTag(tag))` (reusing the app's own `lib/l10n/locale_endonyms.dart`) instead of "Same as device". `'en'` keeps tapping "Same as device", preserving today's exact path and coverage. Alternative considered: add a `ValueKey` per language row for lookup — rejected as an unnecessary production-code change; text-based finding is already this suite's established pattern (e.g. `find.text(l10n.settingsLanguageSystem)`), and `endonymForLocaleTag` already gives an exact, unambiguous string per tag.

4. **Two different kinds of literal string, handled two different ways** (discovered during the task 1 inventory, refining this decision from the original proposal): most of the suite's non-numeric literals — `'Salary'`, `'Groceries'`, `'Other Income'`, `'Other Expense'`, `'Cash & Bank'` — are not test-authored at all. They're the app's own seeded system names, and `lib/l10n/system_name_localizer.dart` already maps each one to its localized display string via `AppLocalizations` getters (`systemCategorySalary`, `systemAccountCashBank`, etc.). The suite should call those getters directly through the dispatched `l10n` instance rather than inventing translations of its own — this is both far less work and guaranteed to match whatever the app actually renders, in every locale, forever. Only a small, genuinely test-authored set needs a real fixture table: two new-group/account names created via dialogs the test drives (`'Euro Group'`, `'Euro Savings'`), two first-week-setup account names (`'My Card'`, `'Pocket Cash'`), one recurring-template name (`'Rent'` — distinct from the `Rent/Mortgage` *category*), one payee name (`'Starbucks'`), and a description/search-term pair (`'Coffee run'` / `'Coffee'`, where the search term must remain a substring of the description in every translated variant). A new `integration_test/acceptance/support/locale_fixtures.dart` defines an `AcceptanceFixtures` value type with exactly these ~8 fields and `fixturesForTag(tag)`, translated for the curated locale set and defaulting to the existing English literal otherwise. Numeric-only entries (amounts, PINs, day-of-month) need no fixture entry either way.

5. **Curated locale set (9 tags, fixed in code):** `ar`, `ur` (RTL — two locales, different script/digit conventions), `hi` (Devanagari, complex conjunct script, no BIP39 wordlist), `ja`, `zh`, `ko` (CJK, all three have BIP39 wordlists — exercises the localized recovery phrase together with double-byte rendering and zero-decimal/no-thousands-separator currency formatting), `fr` (BIP39 wordlist, accented Latin script), `de` (long compound words — layout/overflow stress; no wordlist, exercises the English-fallback recovery-phrase notice), `as` (Assamese — flagged during `onboarding-language-selection` as a lower-review-confidence, AI-drafted locale that already had an ICU-escaping bug). This overlaps deliberately with the locales already spot-checked by hand in `onboarding-language-selection` (Tamil, French, Arabic/Urdu), so this automated tier can supersede some of that manual burden going forward. The list lives as a `const` next to `locale_fixtures.dart`, not derived at runtime, so it's a deliberate, reviewable decision each time it changes.

6. **Onboarding forces a fixed currency (USD) regardless of locale.** Found via a real run, not anticipated in the original design: `onboarding-language-selection` seeds `CurrencySelectionView`'s default from the selected locale (e.g. `ja` → JPY, zero decimal digits), and the suite's own onboarding helpers previously just accepted whatever was pre-filled. Left alone, this breaks nearly every hardcoded amount+currency assertion elsewhere in the suite (`'25.00'`, `'1,000.00 USD'`, ...), since they implicitly assume the English-locale default of USD. Currency-follows-locale already has its own dedicated coverage (`onboarding-language-selection`); this suite exists to verify the rest of the app's behavior *in* each locale, not to re-verify that mapping. Both onboarding entry points now explicitly type `'USD'` into the currency field before continuing, regardless of `kAcceptanceLocaleTag`, so every locale run produces directly comparable, locale-independent amount formatting.

7. **Invocation surface.** `tool/run_acceptance_tests.sh` gains an optional `-l/--locale <tag>` flag (mirroring the existing `-d/--device` flag), defaulting to `en` — an omitted flag reproduces today's invocation exactly. A new sibling script, `tool/run_localized_acceptance_tests.sh -d <device> [-g <group>]`, loops the 9 curated tags, invoking the main script once per tag, and prints a per-locale pass/fail summary with a non-zero exit if any locale failed. Neither script is referenced from `flutter-ci.yml` or any other workflow.

1b. **`staticPrefixOf` replaces the `template('').trim()` trick for matching a localized formatted string's static text.** Found by the corrected full-suite run itself: `l10n.errorLockedUntil('').trim()` (used for a `textContaining` match) only produces a genuine substring of the real rendered text when the template's placeholder is the very last thing in it (true of `lockedUntilDate`, "Locked until {date}") - `errorLockedUntil`'s placeholder is followed by a literal "." ("...locked until {date}."), so the empty-substitution result ("...until .") is never actually a substring of the real text ("...until 2026-10-15."). `staticPrefixOf(template)` substitutes a sentinel character and takes everything before it, which stays correct regardless of where the placeholder sits in the template. Covered by a unit test (`test/acceptance_static_prefix_test.dart`) with one case per placeholder position.

## Risks / Trade-offs

- **[Runtime cost]** Running the full suite once per curated locale multiplies an already multi-hour English run by up to 9x. → Mitigation: fully opt-in/manual; the wrapper script is the only thing that chains locales, and a developer can invoke a single locale directly via the flag for a faster spot-check.
- **[Fixture-table drift]** New test code added later that types in a literal string won't have curated-locale coverage until someone adds it to the table. → Mitigation: document the convention in the harness file's header comment, next to the existing localization note.
- **[Fixture translation isn't reviewed]** Fixture strings are simple test data, not professionally reviewed translations — a plausible-but-wrong fixture wouldn't be caught, since the test only checks round-trip consistency (typed text reappears correctly), not linguistic correctness. → Accepted: this suite validates GUI correctness per script/direction, not translation quality, which is already a known, accepted risk elsewhere (`app-localization`).
- **[RTL layout risk]** Every existing gesture in the suite is a vertical drag or a text/type-based tap (confirmed by inventory — no horizontal swipes), so mirroring shouldn't break gesture mechanics. A real RTL layout bug (clipped button, overlapping text) could still make a `tapReliably` hit-test warning fire or a `find.text` come up empty. → This is exactly the class of bug this change exists to catch: treat such a failure as a real layout bug to fix, not test flakiness to paper over, per this repo's own established acceptance-debugging practice.
- **[English recovery phrase amid localized chrome]** For the 5 non-wordlist tags in the curated set (`ar`, `ur`, `hi`, `de`, `as`), the recovery phrase stays English while surrounding UI is localized — expected, existing behavior. The suite's word-tapping logic already reads words dynamically off-screen rather than assuming English literals, so no change is expected there; verified during the fixture/l10n-site inventory task.

## Migration Plan

N/A — test-only addition. Existing English-only invocations are unaffected since the new locale flag defaults to `en`. Nothing to roll back beyond removing the new files/flags if this doesn't pan out.

## Open Questions

- Should the curated locale list be a single Dart `const` that the shell wrapper reads (e.g. via a tiny `dart run` helper), or duplicated as a literal in the shell script with a comment pointing at the Dart source of truth? Decide during implementation — either is fine at 9 entries.
- Should the curated multi-locale wrapper start macOS-only (matching this repo's primary manual-verification device today) or accept any device from the start? Proposal doesn't restrict by platform; leaning macOS-only initially given runtime cost, revisit if iOS/Android coverage turns out to matter more.

# Repository dependency graph stays acyclic (D1a)

`IdentityRepository`, `AccountRepository`, and core `LedgerRepository` must never form a construction cycle. `LedgerRepository`'s posting path needs the current signing identity and financial-account/category validation; `IdentityRepository.confirmFirstIdentity` needs `AccountRepository` to seed onboarding books; `AccountRepository` needs `LedgerRepository` for opening-balance and closeout postings. Making all three explicit constructor dependencies of each other is not constructible in Dart — the app's DI graph (`main.dart`'s `ProxyProvider` chain) would have no valid construction order.

We decided each repository keeps a small private, read-only duplicate of the other's helper rather than take a full dependency on it: `LedgerRepository` keeps private `_requireActiveFinancialAccount` / `_groupCurrencyFor` / `_currentSigningIdentity()` copies instead of depending on `AccountRepository`/`IdentityRepository`; `InvestmentRepository` keeps private `_requireActiveExpenseCategory` / `_requireActiveIncomeCategory` delegating to the shared, cycle-free `AccountChartReader` leaf rather than depending on `AccountRepository` directly. The dependency graph stays strictly one-directional: leaves (`CategoryRepository`, `PayeeRepository`, core `LedgerRepository`, `AccountChartReader`) sit below `AccountRepository`, which sits below `IdentityRepository`, which sits below `LedgerBackupRepository`/`InvestmentRepository`/others — nothing ever depends back down.

This trades a handful of tiny duplicated read-only queries for a DI graph Dart can actually construct, and for locality: each repository's private copy is small, read-only, and carries no risk of write-behavior divergence from its sibling's copy (both queries return the same answer from the same table). If a shared read seam is ever introduced to remove the duplication, it must stay a leaf itself — a data-only module like `AccountChartReader` that takes only `AppDatabase` — never a dependency that could re-close a cycle.

Established during `architecture-deepening` (2026-08-25) when splitting `LedgerRepository`, and re-applied in every subsequent deepening that touches these repositories (`extract-ledger-chain-store`, `extract-ledger-posting-core`, `finish-chart-catalog-seams`, `extract-active-balance-engine`, `finish-investment-income-category-seam`). See `openspec/changes/archive/2026-08-25-architecture-deepening/design.md` (Decisions D1a, D2) for the original full caller audit and dependency-graph derivation.
